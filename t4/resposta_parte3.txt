1. Que problemas relacionados às estruturas de dados podem ser identificados no código? Por que são problemas, e que alternativas poderiam melhorar a implementação?

Resposta:

1.1. Vetores com capacidade fixa para gerações e espécies

Problema:
Em geracao.c, a geração guarda os indivíduos e as espécies em vetores de tamanho fixo. Em especie.c, cada espécie também guarda seus indivíduos em um vetor fixo. Os limites são definidos em config.h. Ao exceder esses limites, o código depende de assertivas, em vez de conseguir aumentar os vetores.

Por que isso é um problema:
O tamanho da população e o número de espécies ficam ligados às configurações usadas na compilação. O código atual trabalha com 500 indivíduos, então os limites são suficientes para essa configuração; o problema aparece se a população ou o número de espécies precisar crescer.

Alternativa:
Usar listas encadeadas para armazenar indivíduos e espécies. A inserção de novos elementos não depende de reservar antes um vetor com capacidade máxima.

Por que melhora:
As listas não impõem os limites fixos definidos em config.h. Porém, essa mudança exigiria adaptar as operações atuais: o código ordena os vetores por pontuação e escolhe indivíduos por posição, enquanto o acesso a uma posição em uma lista exige percorrê-la. A lista resolve o limite fixo, mas pode tornar essas operações mais lentas. Então não sei até que ponto isso seria vantajoso, é aquilo, perdemos em um lado e ganhamos no outro.

1.2. Busca de neurônios pelo identificador

Problema:
Em individuo.c, a função indivíduo_sinapse_com_ids procura os neurônios de origem e destino passando pelo vetor até encontrar os dois. Como isso acontece durante a comparação entre indivíduos, a busca acaba se repetindo bastante.

Por que isso é um problema:
Quanto maior a rede, mais neurônios podem precisar ser verificados a cada busca. Como a comparação é repetida para vários indivíduos, esse trabalho pode se acumular.

Alternativa:
Manter uma árvore binária de busca auxiliar, usando o identificador do neurônio para encontrar sua posição na rede.

Por que melhora:
A árvore poderia encontrar a posição sem precisar passar pelo vetor inteiro. Isso ajuda se ela estiver organizada; se ficar muito desbalanceada, a busca pode continuar demorada.

1.3. Registro de inovações com limite fixo

Problema:
Em individuo.c, o vetor global inovações tem capacidade fixa de 10.000 posições. A função id_neurônio_entre procura uma inovação percorrendo o vetor desde o início.

Por que isso é um problema:
Quando há mais inovações, a busca demora mais. Se o vetor atingir o limite, o código informa o erro, mas ainda cria uma nova identificação sem guardar a inovação. Se o mesmo par de neurônios aparecer novamente, ele poderá receber outra identificação.

Alternativa:
Usar uma árvore binária de busca para guardar as inovações, ordenada pelo par de identificadores dos neurônios de origem e destino.

Por que melhora:
A árvore não teria o limite fixo do vetor e permitiria procurar pelo par de identificadores. Se estiver bem organizada, a busca também pode ser mais rápida. Se ficar desbalanceada, pode continuar demorada.


2. Que alteração na API de grafos facilitaria seu uso pelo programa de treinamento?

Resposta:

Uma alteração que facilitaria o uso da API definida em grafo.h seria permitir percorrer todas as arestas. Atualmente, a API permite percorrer as arestas que partem de um nó ou chegam a um nó, mas não tem uma operação para percorrer todas de uma vez. Por isso, o código que trabalha com as redes passa pelos nós um a um para visitar as sinapses.

Minha sugestão é adicionar à API de grafo.h um percurso que visite todas as arestas. Para isso, seriam necessárias duas funções: uma para iniciar o percurso e outra para obter a próxima aresta, junto com os números dos nós de origem e destino. Por exemplo: g_inicia_percurso_arestas(grafo) e g_próxima_aresta_global(grafo, &origem, &destino). Com elas, o código não precisaria iniciar uma consulta separada para cada nó. Isso deixa o uso da API mais simples, mas não quer dizer que o percurso vá ficar mais rápido.

Outra sugestão seria adicionar uma função g_remove_aresta(grafo, origem, destino). Atualmente, para remover uma aresta, é preciso chamar g_altera_valor_da_aresta passando NULL como valor. Uma função própria deixaria mais claro que a intenção é remover a aresta, em vez de alterar seu valor, mas claro que essa sugestao é algo mais de organização apenas.
